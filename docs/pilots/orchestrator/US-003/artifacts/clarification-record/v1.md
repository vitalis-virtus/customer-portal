# Clarification Record — US-003 View Own Profile

## 1. Candidate Story

- **ID:** US-003
- **Назва:** View Own Profile
- **Джерело:** [Epic Map](../../../../../product/epic-map.md), EPIC-002 — Self-Service Account Management.
- **Опис із джерела:** «Користувач переглядає дані свого профілю».
- **Goal Epic:** дати користувачу змогу самостійно підтримувати актуальність свого профілю та пароля.
- **Пов'язані правила та вимоги (Epic Map):** BR-002, BR-003, NFR-002.
- **Передумови:** Open Product Dependencies в Epic Map стосуються лише EPIC-003 (US-006, US-007). Для US-003 невирішених продуктових залежностей немає.

## 2. Запропонований Story Type

**FEATURE.**

Обґрунтування: Story походить з Product Foundation (Epic Map) і описує дію користувача, а не технічну ціль (`workflow-policies.md` §16). Для FEATURE обов'язковий зміст специфікації — користувач чи роль, потреба, поведінка, scope.

Тип лише пропонується. Фіксує його SPECIFICATION, погоджує людина на HUMAN_SPEC_APPROVAL.

## 3. Розуміння scope

**У scope:**

- Автентифікований користувач переглядає свій власний Profile (BR-002).
- Перегляд доступний будь-якому автентифікованому користувачу, незалежно від ролі `user` / `admin` (CQ-03).
- Profile містить лише email (CQ-01).

**Поза scope:**

- Зміна даних профілю — US-004.
- Зміна пароля — US-005.
- Перегляд профілю іншого користувача, зокрема адміністратором (BR-002; адміністративні можливості MVP — лише блокування і розблокування, BR-001).
- Повернення ролі користувача в цьому перегляді (CQ-02).
- Будь-які персональні поля профілю, крім email (CQ-01).

## 5. Питання і рішення

### CQ-01 — Склад Profile

- **Контекст:** Business Glossary визначає Profile, але не його склад; API Conventions §7, §15 позначають склад Profile відкритим продуктовим питанням. Із Foundation відомі лише email (BR-003), роль (BR-005, BR-006) і пароль, який розкривати не можна (NFR-002).
- **Варіанти:** A — лише email; B — email і додаткові персональні поля (поіменно, з джерелом даних); C — інший перелік.
- **Рекомендація агента:** A — єдине поле, яке Foundation уже визначає; не вводить нових даних.
- **Рішення людини:** «A — Profile містить лише email. Інші персональні поля поки не додаємо.»
- **decided_by:** owner
- **decided_at:** 2026-11-19T16:38:06Z

### CQ-02 — Роль у перегляді профілю

- **Контекст:** за Glossary Role — ознака доступу, а не дані профілю; користувач не змінює свою роль, тоді як Profile — дані, які він може змінювати.
- **Варіанти:** A — не показувати; B — показувати лише для читання, окремо від даних профілю.
- **Рекомендація агента:** A — узгоджується з визначенням Profile у Glossary.
- **Рішення людини:** «A — роль користувача не входить до Profile і не повертається в цьому перегляді.»
- **decided_by:** owner
- **decided_at:** 2026-11-19T16:38:06Z

### CQ-03 — Доступ адміністратора до власного профілю

- **Контекст:** Glossary відносить Administrator до User, BR-002 говорить про «користувача» загалом, а Product Vision і Personas пов'язують керування профілем із Persona «Користувач порталу» (роль `user`).
- **Варіанти:** A — доступно будь-якому автентифікованому користувачу незалежно від ролі; B — лише ролі `user`.
- **Рекомендація агента:** A — випливає з Glossary (Administrator є User) і BR-002 без обмеження ролей.
- **Рішення людини:** «A — власний Profile доступний будь-якому автентифікованому користувачу, незалежно від ролі (user/admin).»

## 7. Суперечності та ризики

- **Суперечностей із Foundation не виявлено.**
- **Відкрите питання Foundation «Склад Profile»** (API Conventions §15) у межах цієї Story вирішено рішенням людини CQ-01. Сам документ Foundation цей запис не змінює; синхронізація Foundation — поза стадією CLARIFICATION.
- **Ризик для US-004.** За Glossary Profile — дані, які користувач може змінювати, а за CQ-01 Profile містить лише email. Отже, US-004 доведеться вирішити, чи можна змінювати email і як це узгоджується з BR-003. US-003 це питання не вирішує.
- **Ризик формулювання Persona.** Personas пов'язують керування профілем із роллю `user`, а CQ-03 відкриває перегляд і для `admin`. Це не суперечність (Personas описують людей, а не ролі, і позначені як proto-personas), але може потребувати уточнення Personas.
- **FG-01 (Testing Strategy)** не визначено. На вимоги US-003 не впливає, але впливає на Verification Methods на подальших стадіях.

## 8. Handoff для SPECIFICATION

Вимоги й рішення, на які спирається специфікація:

1. **Роль / користувач:** будь-який автентифікований користувач — з роллю `user` або `admin` (CQ-03; Glossary — User).
2. **Потреба:** переглянути дані свого профілю (Epic Map US-003; Personas — Needs).
3. **Поведінка:**
   - автентифікований користувач отримує свій Profile; Profile містить лише email цього користувача (CQ-01);
   - відповідь містить лише дані власного Account; ідентифікатор іншого акаунта передати неможливо (BR-002; API Conventions §3, AR-007);
   - роль користувача у відповіді не повертається (CQ-02);
   - пароль чи будь-які облікові дані у відповіді не повертаються (NFR-002);
   - запит без чинної сесії відхиляється як «не автентифіковано» (`401`, `unauthenticated`), зокрема запит заблокованого користувача, надісланий після завершення блокування (AR-006, BR-007, Security Conventions §7).
4. **Scope:** розділ 3 цього запису.

Технічні деталі реалізації (форма підресурсу під `/api/v1/me`, представлення відповіді, структура DTO) не вирішуються тут і передаються Technical Design у межах API Conventions.
