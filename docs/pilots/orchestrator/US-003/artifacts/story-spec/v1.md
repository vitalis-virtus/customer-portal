# Story Spec — US-003 View Own Profile

Вхідний [clarification-record v1](../clarification-record/v1.md) теж пілотний і не зареєстрований. Нижче «CR» означає цей запис. Технічні факти Architecture Foundation тут наведено лише так, як їх записано в CR §4 і Handoff (CR §8).

## 1. Story

- **ID:** US-003 — View Own Profile
- **Epic:** EPIC-002 — Self-Service Account Management
- **Джерело:** [Epic Map → EPIC-002](../../../../../product/epic-map.md#epic-002--self-service-account-management): «Користувач переглядає дані свого профілю».
- **Story Type:** **FEATURE**. Тип збігається з пропозицією CR §2. Story походить із Product Foundation (Epic Map) і описує дію користувача зі спостережуваною поведінкою (`workflow-policies.md` §16). Тип погоджує людина на HUMAN_SPEC_APPROVAL.

Обов'язковий зміст FEATURE:

- **Користувач / роль:** будь-який автентифікований користувач — з роллю `user` або `admin` (CQ-03; Glossary → User: Administrator також належить до User). Основна Persona — [Користувач порталу](../../../../../product/personas.md#persona-1-користувач-порталу); застереження щодо `admin` — розділ 6.
- **Потреба:** переглянути дані свого профілю (Epic Map → US-003; Personas → Needs: «Переглядати та змінювати дані свого профілю»; Goals: «Підтримувати актуальність даних свого профілю»).
- **Поведінка:** розділи 3 і 4.
- **Scope:** розділ 2.

## 4. Acceptance Criteria

Нотація: **A** — Account з роллю `user` і email `alice@example.com`; **B** — Account з роллю `user` і email `bob@example.com`; **D** — Account з роллю `admin` і email `admin@example.com`. «Чинна сесія X» — сесія Account X, отримана способом, який визначає US-002. «Запит перегляду» — запит перегляду власного Profile; його маршрут під `/api/v1/me` і форму відповіді визначає Technical Design (розділ 7). «Успішна відповідь» — відповідь, що повертає Profile; її код визначає Technical Design. Якщо умова не вказує інше, A, B і D існують і не заблоковані.

## 6. Ризики й обмеження

**Ризики (успадковано з CR §7):**

- **Foundation не синхронізовано.** Склад Profile в API Conventions §15 і Glossary → Profile досі позначено відкритим. У межах US-003 його вирішено рішенням CQ-01, яке зафіксовано лише в CR. Чи оновлювати Foundation — рішення людини поза цією стадією.
- **Ризик для US-004.** За Glossary Profile — дані, які користувач може змінювати, а за CQ-01 Profile містить лише email. US-004 має вирішити, чи можна змінювати email і як це узгоджується з BR-003. US-003 це не вирішує.
- **Формулювання Persona.** Personas пов'язують керування профілем із роллю `user`, а CQ-03 відкриває перегляд і для `admin`. Суперечності немає, але Personas може знадобитися уточнити.
- **FG-01 (Testing Strategy) не визначено.** Verification Methods тут описують лише, що спостерігати; інструменти й рівні тестів визначають Testing Strategy і Testing Approach `implementation-plan`.

**Прогалини Foundation:**

- **NFR-001** має статус `NEEDS_CLARIFICATION`. На вимоги US-003 не впливає, але механізм сесії, від якого залежить перевірка AC, визначає US-002.

**Обмеження (з CR §4):**

- Self-service ресурси — під `/api/v1/me`; користувач визначається лише з Actor, маршрут не має параметра з ідентифікатором акаунта (API Conventions §3, AR-007).
- Кожен захищений запит проходить перевірку сесії; без чинної сесії — `401`, `unauthenticated` (AR-006, Security Conventions §7, API Conventions §9).

## 7. Відкрито для Technical Design

Специфікація свідомо не вирішує таких питань:

1. Форма підресурсу під `/api/v1/me` і HTTP-метод запиту перегляду (CR §8).
2. Код успішної відповіді, представлення відповіді і структура DTO (CR §8).
3. Чи містить відповідь, крім email, неперсональні технічні поля (наприклад, ідентифікатор Account). CQ-01 виключає лише персональні поля Profile; AC-03 перевіряє тільки їх.
4. Обробка додаткових параметрів запиту, якими намагаються вказати інший Account (AC-07): відхилення чи ігнорування. AC вимагають лише, щоб дані іншого Account не поверталися.
5. Спосіб, яким перевірка сесії відхиляє запит заблокованого користувача (AC-13): відкликання сесій під час блокування чи перевірка стану Account на кожному запиті. Пов'язано з US-006.

**Увага для HUMAN_SPEC_APPROVAL.** Пункти 3 і 4 впливають на спостережувану відповідь (склад тіла; `400` чи успіх для запиту з додатковим параметром). Їх немає серед технічних деталей Handoff CR §8, і CR їх явно не вирішує. Специфікація передає їх Technical Design у межах API Conventions і не обирає варіанта. Людина на HUMAN_SPEC_APPROVAL або приймає це як межу Technical Design, або, якщо вважає це продуктовим рішенням, повертає ці пункти на CLARIFICATION.
