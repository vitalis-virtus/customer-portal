## 3. Розуміння scope

**У scope:**

- створення нового Account людиною без автентифікації (публічна операція);
- вхідні дані реєстрації: лише email і пароль (CQ-05);
- нормалізація, перевірка формату та унікальності email (CQ-01, BR-003);
- перевірка пароля за політикою пароля (CQ-04);
- явне повідомлення про конфлікт, якщо email уже зареєстровано (CQ-02);
- призначення ролі `user` новому користувачу (BR-005, BR-006);
- збереження пароля відповідно до NFR-002.

**Поза scope:**

- автоматичний login і створення сесій після реєстрації (CQ-03) — належить US-002;
- поля Profile під час реєстрації (CQ-05); склад Profile лишається відкритим для US-003/US-004;
- email verification ([Product Vision — Out of Scope](../../product/product-vision.md#out-of-scope));
- уточнення NFR-001 — за [Security Conventions §12](../../architecture/security-conventions.md#що-треба-закрити-до-реалізації-us-001-і-us-002) виконується на Clarification US-002;
- захист від автоматизованого перебору (P3) — US-002;
- створення користувачів із роллю `admin` (Administrator Provisioning, P6) — US-006/US-007.

### CQ-01 — Регістр, нормалізація і формат email (BR-003)

- **Контекст:** BR-003 не визначає, чи однакові email, що відрізняються регістром. [Persistence Conventions §13](../../architecture/persistence-conventions.md#відкриті-питання) тримає «Регістр і нормалізація email» як OPEN для Clarification US-001; від нього залежать форма unique constraint і індексу.
- **Підпитання:** (а) trim; (б) регістр — уся адреса чи лише домен; (в) що зберігати; (г) формат.
- **Варіанти:**
  - A — trim + уся адреса без урахування регістру; зберігати як введено, унікальність за lower-case формою;
  - B — trim + lower-case, зберігати канонічну форму;
  - C — без урахування регістру лише домен (RFC 5321);
  - D — без нормалізації.
- **Рекомендація агента:** A; для (г) — мінімальна синтаксична перевірка: одна `@`, непорожні local-part і домен, максимум 254 символи.
- **Рішення людини:** «cq-01 - A»; щодо формату (г): «CQ-01 - погоджую».
- **decided_by:** owner
- **decided_at:** (а–в) 2026-11-18T14:13:48Z; (г) 2026-11-18T14:19:29Z

### CQ-02 — Дубль email під час реєстрації (P5, частина реєстрації)

### CQ-04 — Політика пароля (P4)

- **Контекст:** P4 у [Security Conventions §12](../../architecture/security-conventions.md#продуктові-питання) — OPEN, US-001 і US-005, потребує рішення власника продукту.
- **Підпитання:** (а) мінімальна довжина; (б) одиниця довжини; (в) вимоги до складу; уточнення — які класи і що вважати літерою.
- **Варіанти:** A — ≥ 8 символів без вимог до складу; B — ≥ 12 без вимог до складу; C — ≥ 8 і обов'язкові класи символів; D — інше. Для C: C1 — літера + цифра; C2 — велика + мала + цифра; C3 — C2 + спецсимвол; C4 — 3 з 4 класів. Літера: U — будь-яка Unicode-літера з регістром; L — лише латиниця.
- **Рекомендація агента:** A, довжина в code points (NIST SP 800-63B-4 не радить вимог до складу). Після вибору C — C1, літера U, довжина в code points.
- **Рішення людини:** «cq-04 - C»; «C2 — щонайменше одна велика літера, одна мала і одна цифра»; літера — «L»; одиниця довжини — «байтах».
- **Підсумок рішення:** мінімум 8 байтів UTF-8; щонайменше одна велика латинська літера `A–Z`, одна мала латинська літера `a–z` і одна цифра `0–9`. Рекомендацію агента не прийнято; розбіжність із NIST SP 800-63B-4 зафіксовано (розділ 7).

## 7. Суперечності та ризики

**Суперечностей із Foundation не виявлено.** Рішення CQ-01, CQ-02 і CQ-04 заповнюють пункти, які Foundation явно залишає відкритими для Clarification US-001, і не змінюють погоджених правил.

**Ризики:**

- **R-01 — перелічення акаунтів (CQ-02).** `409` для дубля email дозволяє дізнатися, чи зареєстровано email. Це частково знецінює погоджене нерозкриття причин невдалого login ([Security Conventions §7](../../architecture/security-conventions.md#login)), яке стосується лише login. Без захисту від автоматизованого перебору (P3) ризик масового перелічення через реєстрацію не обмежено.
- **R-02 — мінімальна довжина в байтах (CQ-04).** Символ поза ASCII займає 2–4 байти UTF-8, тому пароль із такими символами може мати менше 8 символів і пройти перевірку довжини. Реальна мінімальна стійкість для таких паролів нижча, ніж для ASCII.
- **R-03 — вимоги до складу пароля (CQ-04).** Вимога класів символів розходиться з рекомендацією NIST SP 800-63B-4. Паролі лише з нелатинських літер і цифр перевірку не пройдуть (літера — лише `A–Z`/`a–z`). Foundation такого правила не забороняє.
- **R-04 — FG-01 (Testing Strategy).** Документа немає; за workflow-policies.md §15 перша реальна Story не реєструється у Workflow, доки його не створено. Для пілоту не блокує.
- **R-05 — значення timeout-ів і лімітів HTTP-сервера** відкладено до Infrastructure Bootstrap ([Security Conventions §12](../../architecture/security-conventions.md#що-треба-закрити-до-реалізації-us-001-і-us-002)). Блокує реалізацію, не специфікацію.
- **R-06 — синхронізація Foundation.** P4, P5 (частина реєстрації) і «Регістр і нормалізація email» у Security, API і Persistence Conventions досі позначені OPEN. Після погодження специфікації їх треба синхронізувати окремою роботою (Foundation Change Request); цей артефакт Foundation не змінює.

**Прогалини, які успадковують SPECIFICATION і Technical Design** (не критичні для PASS: правило погоджено в представленому вигляді):

- **G-01 — lower-case для не-ASCII email (CQ-01).** Не визначено, чи «lower-case форма» означає ASCII lowercase чи Unicode case folding. Правило формату не забороняє не-ASCII символи. Впливає на форму unique constraint ([Persistence Conventions §13](../../architecture/persistence-conventions.md#відкриті-питання)).
- **G-02 — одиниця межі 254 (CQ-01).** Не визначено, символи чи октети; RFC 5321 рахує октети.
- **G-03 — trim і збережене значення (CQ-01).** Чи зберігається email після trim — див. розділ 8, п. 3.

## 8. Handoff для SPECIFICATION

**Story Type (пропозиція):** FEATURE. **Роль:** людина без облікового запису, яка після реєстрації стає користувачем із роллю `user`. **Потреба:** самостійно створити обліковий запис (Personas — Needs; Product Vision — ціль 1).

**Вимоги й рішення:**

1. Реєстрація — публічна операція, доступна будь-кому (BR-004; API Conventions §9).
2. Вхідні дані: лише email і пароль. Поля Profile не приймаються (CQ-05).
3. Email:
   - пробіли на краях обрізаються (CQ-01);
   - порівняння для унікальності — уся адреса без урахування регістру, за lower-case формою (CQ-01, BR-003);
   - зберігається email як введено (CQ-01). Чи зберігається значення до чи після trim, людина окремо не вирішувала; читання «після trim» — інтерпретація агента, яку SPECIFICATION має підтвердити (G-03);
   - валідний формат: рівно одна `@`, непорожні local-part і домен, довжина ≤ 254 символи (CQ-01);
   - email не передається в URL і не логується (API Conventions §2; Security Conventions §9).
4. Пароль:
   - мінімум 8 байтів UTF-8 (CQ-04);
   - щонайменше одна велика `A–Z`, одна мала `a–z` і одна цифра `0–9` (CQ-04);
   - технічна межа — 1024 байти; пароль — непрозорі байти без trim і нормалізації (Security Conventions §6);
   - пароль не зберігається у відкритому чи відновлюваному вигляді, не повертається у відповідях, не потрапляє в логи й повідомлення про помилки валідації (NFR-002; Security Conventions §6).
5. Якщо email (за правилом порівняння з п. 3) уже зареєстровано — Account не створюється, відповідь явно повідомляє про конфлікт (`409`) (CQ-02; API Conventions §8).
6. Новий користувач отримує роль `user` і лише її (BR-005, BR-006).
7. Реєстрація не створює сесій і не виконує login (CQ-03).
8. Ідентифікатор нового Account — UUID v4 (Persistence Conventions §6).

**Для Acceptance Criteria варто покрити:** успішну реєстрацію; дубль email, зокрема з іншим регістром і пробілами на краях; невалідний формат email; пароль коротший за 8 байтів; пароль без великої, малої чи цифри; пароль понад 1024 байти; відсутність пароля у відповідях і логах; роль `user` у створеного користувача; відсутність сесії після реєстрації.

**Не визначено і не потрібно для специфікації US-001:** конкретний URL маршруту в `/api/v1/auth` (визначає SPECIFICATION/Technical Design у межах API Conventions); значення timeout-ів і лімітів HTTP-сервера (Infrastructure Bootstrap); точні коди помилок валідації в межах формату API Conventions §8.
